# Guide：每轮改动记在哪里（README 不当变更日志）

> 适用：一轮修复或功能做完，要把「这轮改了什么、为什么」写进文档时；以及改 README 时。
> 来源：[[2026-09-26-readme-changelog-removal]]（README 里积了 14 段「YYYY-MM-DD 变动」，删之前逐条核对）。

## 规则

1. **README 只写使用者要知道的现状**：能做什么、怎么用、有哪些限制和豁免（比如「语言支持」的豁免表）。
   某个行为变了，就**原地改**描述现状的那句话或那一行表格，不在后面追加一段带日期的「变动」。
2. **每轮修了什么、根因、教训**分别写进：
   - 对应阶段的 `docs/design/<phase>/implementation-progress.md`（按日期的进度对账，写改了哪些文件、哪些行为）；
   - 对应设计文档里受影响的那一节（机制、判据）；
   - `llmdoc/memory/reflections/`（过程教训），可复用的判据再提升进 `llmdoc/guides/`。
3. **同一件事只在一处写全**，其他地方放链接。README 的「文档导航」已经指向各阶段的 `implementation-progress.md`
   和反思目录，不需要在 README 里再复述一遍。

## 为什么

- **读者不对**：README 的读者是要用 wangshu 的人。harness 的 skip 条件、nightly 的超时预算、去重键怎么选，
  这些对他们没用，只会把真正要看的内容（快速开始、语言支持、文档导航）往下挤。
- **副本会过时，而且没人发现**：后来的更正只落在设计文档或反思里，README 那份旧说法原样留着。
  这次核对时，14 段里至少有三处已经被推翻（`--retry-all-errors` 被写成重试超时的前提、infra issue 按
  `run_id` 去重、一串已经改过的超时数字）。多一份副本，就多一处要同步却没有任何检查会提醒的地方。

## 已经有一串日志要清理时

删之前逐条核对：把每段拆成可核对的事实，对每条在 `docs/design/`、`llmdoc/`、README 其他部分找到对应记录。
只在 README 里出现、而且是使用者能感知的行为，先挪到对应文档再删。核对时发现别处的记录本身过时了
（这次找到了 #262 之前的行号残留清单、nightly workflow 注释里的旧预算数字），一并修掉。
