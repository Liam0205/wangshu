# 确认一个上游修复是否随某版本发布，判据在源码里而不在发布说明里（#180，commit `d9c3cf6`）

> 范围：issue #180（chore，Go 1.27 正式升级与 fuzz deadline 文档同步），分支
> `chore/180-go127-upgrade`。**这段范围说明在写下时就是错的,保留并更正,因为它本身是一个实例**:
> 它说「1 个 commit、`scripts/go-fuzz.sh` 全部零改动」,而添加这篇反思的那个 commit(`ab17328`)
> 同时就改了 `go-fuzz.sh` 里那段「上游修复未合入」的注释。写范围说明的时候我照的是**打算改什么**,
> 不是**实际改了什么** —— 而一个来查「那句过期的 CL 774140 到底修没修」的人,会被这句话告知没修。
>
> 实际范围(共 4 个 commit):`go.mod` 1.26.2 → 1.27.0;`benchmarks/` 与 `benchmarks/pineapple/`
> 两个 `replace` 根模块的子模块一并跟上(审计发现漏了会让 CI 挂);
> `docs/design/engineering.md` §1.1、`scripts/go-fuzz.sh` 的上游状态注释、两个 README 的
> 「Go 1.25+」、`06-backends.md` 的 go.mod 引用与那个从未实现的版本矩阵,全部按实际状态更正。
> 产品代码与测试零改动。

## 任务

issue #180 是一个**等上游的 chore**，它的阻塞条件写得很具体：

> Go 1.27 正式版发布，且确认包含 golang/go#75804 修复。

写下这条条件时（2026-07-24）的现状是：Go 官方仓库只有 `go1.27rc1` / `go1.27rc2`，没有正式
tag；`go1.27rc2` 标记于 2026-07-07，早于 #75804 的修复；主线修复已提交，但面向
`release-branch.go1.27` 的回移 CL 804900 还是 `NEW`。所以两个条件当时都不成立，issue 就停在
那里等。

本轮要回答的就是「这两个条件现在成立了吗」，而**第二个条件比第一个难**：第一个查 tag 就完了，
第二个要证明「这个版本里真有那个修复」。

## 验证过程（本轮的重点）

### 第一步：正式 tag 存在，本机工具链已经是它

`go1.27.0` 正式 tag 存在，而且除 rc1 / rc2 之外还多了一个 rc3 —— 也就是说 rc2 之后上游又收了
一轮改动才发正式版，这与「修复在 rc2 之后才进来」是相容的，但它**只是相容，不是证据**。本机
工具链已经是 `go1.27.0`（`go version` 与 `go env GOROOT` 都确认）。

第一个条件到这里就成立了。第二个条件不能靠 tag 号回答。

### 第二步：不看发布说明，读被安装的那份源码

最省事的做法是去翻 Go 1.27 的发布说明或者看 issue 页面上的状态标记。本轮**没有这么做**，而是
直接去读被安装的那份工具链源码。`$GOROOT/src/internal/fuzz/fuzz.go` 里的抑制检查现在是：

```go
if err == ctx.Err() || err == fuzzCtx.Err() || isInterruptError(err) {
	// Suppress cancellation errors and terminations due to SIGINT.
	// The messages are not helpful since either the user triggered the error
	// (with ^C) or another more helpful message will be printed (a crasher).
	//
	// Also check ctx.Err() because when ctx's deadline expires, there
	// is a window where ctx.Err() is set but fuzzCtx (a child) has
	// not yet been canceled. See go.dev/issue/75804.
	err = nil
}
```

这段东西给出的是**两层证据**，而且两层都是代码级的：

1. **表达式变了**。原来只检查 `err == fuzzCtx.Err()`（这正是本仓 `scripts/go-fuzz.sh` 注释里
   写着的那个检查），现在多了 `err == ctx.Err()` 这一项 —— 也就是父 context 的 deadline
   一侧也被纳入抑制。
2. **注释逐字引用了那个 issue 号**，`go.dev/issue/75804`，并且用文字描述了竞态窗口：ctx 的
   deadline 到期后存在一个窗口，`ctx.Err()` 已置位而子 context `fuzzCtx` 尚未被 cancel。

第二层里还有一件顺带的确认：这段注释描述的窗口，与本仓 `scripts/go-fuzz.sh` 顶部注释里**当年
自己推断**的那个窗口完全一致（那条注释写的是「context 取消传播是先关父 done channel、后 cancel
子 context，留下一个 `ctx.Err()` 已置位而 `fuzzCtx.Err()` 仍为 nil 的窗口」）。当年那是从症状
反推出来的机制假设，现在上游用自己的注释确认了同一个机制。

### 第三步：版本对照 —— 这才是关键的一步

看到 1.27 里有这段代码，**不能**推出「这是 1.27 引入的」。它完全可能一直都在，而 #75804 的
症状另有原因、或者那条 issue 讲的是别的地方。只凭第二步就下结论，证明的是「存在」而不是
「引入」。

所以又拉了 upstream 同一个文件的两个 tag 做对照，数 `issue/75804` 这个字符串的出现次数：

| tag | `issue/75804` 出现次数 |
|---|---|
| `go1.26.2`（升级前本仓用的版本） | **0** |
| `go1.27.0` | **1** |

0 对 1 才排除了「1.27 里本来就有」这个可能。选 `go1.26.2` 做对照项不是随便选的 —— 它正是
本仓升级前 `go.mod` 里写的那个版本，所以这次对照回答的恰好是「相对我们原来在用的东西，这是
新增的吗」，而不是一个抽象的「历史上什么时候加的」。

## 本轮做了什么

- **`go.mod`**：`go 1.26.2` → `go 1.27.0`。所有 workflow 都用 `go-version-file: go.mod`
  取版本（`ci.yml` 七处、`nightly-diff-fuzz.yml`、`bench-acceptance.yml`、
  `bench-vs-luajit.yml` 各一处），所以改这一处就等于全部切换，不需要逐个 workflow 改。
- **依赖不动**：`wazero v1.12.0`、`golang.org/x/sys v0.44.0` 与 #180 列的兼容目标一致，
  本轮无需动。
- **`docs/design/engineering.md` §1.1**：「上游修复未合入」那句按实际发布状态改写，并把上面
  第二、三步的证据写进去（抑制检查的新表达式、注释引用的 issue 号、0 次对 1 次的版本对照），
  而不是只写一句「已发布」。

### 验证

- `build` / `vet` / `gofmt` / `golangci-lint`（0 issues）；
- 全套测试；
- 四个构建变体：p3 / p4 × 有无 `wangshu_profile`；
- `-race ./internal/...`；
- oracle / cgo 差分与 corpus 回放；
- 官方 Lua 套件、difftest、`make test-scripts`；
- 七个 target 的 fuzz smoke —— **#75804 重试 0 次**。

## 一个明确的取舍：那次条件重试保留

#180 的 checklist 里有一条是「评估并**删除** `scripts/go-fuzz.sh` 中只为 golang/go#75804
保留的一次条件重试」。本轮**明确不删**，理由写进了 engineering.md §1.1：

- 它是目前**唯一**区分「真 crasher」与「工具链竞态」的判据（判据本身是「失败输出含 deadline
  字样**且**无 `Failing input written to` crasher 落盘」）。删掉之后一旦判错，代价的方向是最
  坏的那一侧：**真 bug 被当成噪声重试掉**；
- 它的触发频率本来就低 —— 约 450 个 job 里 9 次。一次 30 秒 smoke 跑出 0 次重试，**不足以
  证明**修复生效，因为在原来那个频率下，一次这么短的 smoke 本来就极可能是 0 次；
- 修复真的生效之后，这个数字应当在 nightly 上自然归零(归零只是**必要条件之一**:判据钉在症状上,归零只说明那一条成因停了;还要确认没有别的机制会产生同样症状)(归零只是**必要条件之一**:判据钉在症状上,归零只说明那一条成因停了;还要确认没有别的机制会产生同样症状)。**等实测归零再删，就有数据背书而不是
  靠推断** —— 这也是 #180 那条「评估并删除」的正确执行顺序：先评估，评估结论是证据还不够，
  于是这一轮只做「升 go.mod + 改文档描述」。

## 教训

### 教训 1：确认一个上游修复是否随某版本发布，要读那个版本的源码，而不是读发布说明或 issue 状态

**核心断言**：发布说明、issue 状态标记、CL 的 merge 状态，全都是**关于**那个修复的二手陈述，
而且各自会在不同的时点、以不同的粒度滞后 —— 主线合入不等于回移，回移 CL 合入不等于进了哪个
tag，发布说明只挑值得写的条目写，一个内部包的竞态修复完全可以不出现在里面。唯一能直接回答
「我手上这份工具链有没有这个修复」的东西，是**我手上这份工具链的源码**。

本轮的判据是两条代码级痕迹：抑制检查的**表达式变了**（多了 `err == ctx.Err()` 这一项），并且
**紧邻注释逐字引用了那个 issue 号**（`go.dev/issue/75804`）。第二条尤其便宜 —— Go 这类项目的
惯例是修 bug 时在注释里留 issue 链接，所以「grep issue 号」往往一步就能定位到修复本身。

**判据**：凡「某修复是否已发布 / 是否在我用的这个版本里」类问题，去被安装的那份源码里找**那个
修复本身**的痕迹，而不是去找关于它的陈述。手法有三层，按成本从低到高：① grep issue 号（修复
注释常带链接）② 读那段逻辑，看被修的表达式 / 分支有没有变 ③ 写一个能触发原症状的最小程序实测。
前两层是本轮用的，够用；第三层在症状可稳定触发时才划算，而 #75804 是低频竞态，实测反而是三层
里最弱的证据（见教训 3）。

这与 [[design-claims-vs-codebase-physics]] §5「时间维度」里「外部依赖现状过期」那一格是同一族，
但方向相反：那一格讲**文档里的外部依赖现状会过期**（P4 设计稿写「wazero 用 internal/engine/
compiler」而它已切 wazevo），本条讲**判断外部依赖现状时该拿什么当判据** —— 都是拒绝把二手陈述
当事实，一个管读到的、一个管自己去查的。

### 教训 2：「在新版本里看到了修复代码」不等于「这是新版本引入的」，必须与旧版本对照

**核心断言**：一次「X 在版本 N 里存在」的观察，逻辑上只支持「存在」这个结论。要支持「N 引入了
X」，需要的是一对观察：X 在 N 里存在，**且** X 在 N-1 里不存在。少了后一半，「一直都在」这个
解释没有被排除 —— 而这个解释一旦成立，整条推理就反过来了：如果那段代码一直都在，那它显然没能
防住本仓遇到的假失败，于是「升上去就好了」这个结论也就不成立。

本轮差一点只凭第二步就下结论。真正排除掉「本来就有」的是那次对照：拉 upstream 同一个文件的两个
tag，`go1.26.2` 里 `issue/75804` 出现 **0** 次、`go1.27.0` 出现 **1** 次。对照项选
`go1.26.2` 而不是别的版本，是因为它正是本仓升级前在用的那个 —— 这样这次对照回答的就是「相对
我们原来那份，这是新增的吗」，恰好是决策真正需要的那个问题。

**判据**：任何「X 在版本 N 里存在」的观察，都要配一次「X 在版本 N-1 里不存在」的观察，否则你
证明的是「存在」而不是「引入」。对照项优先选**自己原来在用的那个版本**，因为要回答的问题是
「相对现状这是不是变化」，不是「历史上哪一版加的」。计数式对照（同一字符串在两个 tag 里各出现
几次）比读 diff 便宜，作为第一刀足够。

### 教训 3：一次通过不足以撤掉一层保护，尤其当那层保护正是用来区分真假失败的

**核心断言**：一个观察能不能支持「这层保护可以撤了」，取决于它与那层保护的**历史触发频率是否
同量级**。本轮的观察是一次 30 秒 fuzz smoke 里 #75804 重试 0 次；历史频率是约 450 个 job 里
9 次。在那个频率下，一次这么短的 smoke 本来就极可能是 0 次 —— 也就是说，**这个观察在「修复
生效」与「修复没生效」两个假设下几乎是同一个结果**，因此它对该不该删这个问题没有区分能力。

而这层保护的性质让代价特别不对称：它区分的是「真 crasher」与「工具链竞态」。删错了之后，失效
方向不是「多重试一次浪费时间」，是**真 bug 被当成噪声重试掉** —— 而重试成功之后 CI 是绿的，
这个错误不会留下任何痕迹。一个「防误判」的机制被误撤之后的症状，恰好是「什么都没发生」。

**判据**：撤掉一个「防误判」的机制之前，要有与它**历史触发频率同量级**的观测证明它不再需要；
而且优先用生产环境（本仓是 nightly）的自然观测，而不是一次专门跑的验证 —— 专门跑的验证时长
通常远短于机制的触发周期，而自然观测的时长本来就是那个周期。自查办法：说「这一轮跑干净了所以
可以删」之前，先算一遍「按历史频率，这一轮跑这么久本来该出现几次」，答案接近 0 就说明这一轮
什么都没证明。

这与 [[prove-the-path-under-test]] 里「调紧一个 harness 的资源限制之后要注入一个必须被发现的
缺陷」是同一条纪律的两个方向：那条讲**收紧**之后要证明检测能力还在，本条讲**撤掉**之前要证明
它已经不需要了；两边都拒绝把「这一轮是绿的 / 这一轮没触发」当成结论，因为这两种机制的失效方式
都是安静的。

## Promotion 决策

- **教训 1 → [[design-claims-vs-codebase-physics]] §5**：「主张 vs 实际」那一族的新一格 ——
  此前 §5 的「外部依赖现状过期」管的是**文档里写的**外部依赖现状会过期，本条管**判断外部依赖
  现状时拿什么当判据**（「上游发布说明 vs 工具链源码」）。
- **教训 2 → [[design-claims-vs-codebase-physics]] §5**：与教训 1 同族、紧接其后 ——
  「存在」与「引入」是两个命题，只查新版本得到的是前者。
- **教训 3 → [[prove-the-path-under-test]] 新节「什么时候可以撤掉一个兜底机制」**：既有的
  §4.6「为某个 bug 加的 skip 必须随那个 bug 一起撤掉」讲的是**该撤而没撤**，本条讲反面 ——
  **撤之前要有多少证据**，两条构成同一件事的两个方向，故紧邻成节。
