# 删掉 #75804 条件重试，以及删测试时一起删掉的覆盖（2026-09-26，#180）

> 范围：issue #180 的最后一项 checklist。代码改动在 `scripts/go-fuzz.sh`（删 `run_target` 里的 `for attempt in 1 2`
> 循环与重试分支、改头注释）、删除 `scripts/test-go-fuzz-retry.sh`、`Makefile` 的 `test-scripts`、`ci.yml` 的
> test-scripts job 注释、`scripts/test-nightly-fuzz-classify.sh` 的一条诱饵日志行、`nightly-diff-fuzz.yml` 的注释与
> `::error::` / `::warning::` 文案（step 超时上限与 budgetcheck 阈值的数值**没有动**，这是用户明确要求的）。
> 文档同步在 `docs/design/engineering.md` §1.1、README、[[unreproducible-crasher-triage]] 分类表。#180 要等 PR 合入后再关。

## 任务

08-27 那一轮（[[2026-08-28-go127-upgrade-verification]] 教训 3，guide 见 [[prove-the-path-under-test]] §4.6a）
升级到 Go 1.27 后**明确不删**这次重试，并写下两条撤除条件：与历史触发频率同量级的归零观测，以及确认没有别的机制
会产生同样的症状。本轮回答这两条现在是否成立，成立就删。

## 结果

- **条件 (a)，归零观测**：升级前 120 次 nightly（2026-08-07 至 08-27），1851 次 fuzz 目标运行里重试 14 次
  （分布在 13 个 run）；升级后 123 次（2026-08-28 至 09-25），2199 次运行里 **0 次**，日志中的
  `context deadline exceeded` 也是 0。按升级前约 0.76% 的触发率，2199 次全为 0 的概率约 5.6×10⁻⁸。
  这次观测与 08-27 那次 30 秒 smoke 不同，它与触发频率同量级，§4.6a 的判据得到满足。
- **对照组的作用**：统计方法是 grep 日志里的 `hit golang/go#75804`。只看升级后的 0 次，无法排除「grep 写错了、
  本来就数不到」这个解释；同一条 grep 在升级前的日志里数到了 14 次，这个解释才被排除。这与 08-28 教训 2
  （「在新版本里看到修复」要配一次「旧版本里没有」的观察）是同一种推理：一个 0 要配一个非 0，才说明测量本身是有效的。
- **条件 (b)，没有别的机制产生同样症状**：读 Go 1.27 源码，能把 deadline 报成测试失败的只有
  `internal/fuzz/fuzz.go` 里 `-fuzztime` 那个 `context.WithTimeout`，而 `stop()` 已检查 `ctx.Err()`；worker 内部其余
  `WithTimeout`（单输入、最小化）超时后安静结束或原样返回 crasher；本仓 fuzz harness 不用 `SetContext` 也不用
  `WithTimeout`；1.27.0 → 1.27.1 的 `internal/fuzz` 与 `testing` 没有改动（CI 按 `go.mod` 装 1.27.x）。
- **删除后失效方向变了**：保留重试时担心的是真 crasher 被重试掉、CI 是绿的、没有人发现；删除之后，如果还有未知机制
  产生这个症状，nightly 会变红并自动开 bug issue。这是多报而不是漏报，所以删除本身带有自我检查。§4.6a 要求「先问
  撤错的失效方向」，这里的答案是撤错的代价会自己暴露出来；按 §4.6a 的说法，会自己报出来的失效对应较低的证据门槛。

## 期望与实际

| 期望 | 实际 |
|---|---|
| 删掉重试只是删一个循环和一个分支，改写之后 `bash -n` 通过、`make test-scripts` 全绿就说明脚本没坏 | 改写把 `run_target` 之后的目标发现循环和「没找到目标」检查一起截掉了；两项检查照样全绿，因为它们都不会让 `go-fuzz.sh` 真正执行 |
| `test-go-fuzz-retry.sh` 只测重试逻辑，随重试一起删掉是理所当然的 | 它同时是 `test-scripts` 里**唯一**端到端驱动 `go-fuzz.sh` 的测试；剩下的三个自测（`test-cover.sh`、`test-fetch-lua-tarball.sh`、`test-nightly-fuzz-classify.sh`）都不运行 `go-fuzz.sh` |
| `git show --stat` 里 `go-fuzz.sh` 变动 203 行，大部分是去掉循环后的缩进变化，逐行看不出问题 | 按 `git diff -w` 看只有 53 行（+11 / −42），非注释改动应当只有三处：循环头、重试分支、循环尾；多出来的那一段就是被截掉的尾部 |

## 出了什么错

1. **改写工具截掉了脚本尾部**。用一段 python 替换 `run_target` 里的循环，结果 `run_target` 之后的整段
   （`while read ... done < <(grep ...)` 目标发现循环和「没找到目标」检查）都没了。具体是替换区间的结束点定错还是写回
   时截断，本轮没有追查。
2. **两项检查都看不见它**。截断后的脚本停在一个函数定义之后，语法完全合法，`bash -n` 必然通过；`make test-scripts`
   全绿，因为覆盖 `go-fuzz.sh` 的那个自测已经在同一次改动里删掉了。
3. **带着它提交的后果**：stub 显示 deadline / crash / pass 三种模式都是 `fuzz-calls=0`、rc=0，也就是说脚本什么都
   不跑就以成功退出，连「一个目标都没找到」的检查也一起没了。这恰好是本轮删除论证里最想避免的那种失效：没有任何
   fuzz 在运行，而结果是绿的。本轮没有核实 nightly 的其他检查（例如 budgetcheck 或分类脚本）能不能发现「一个目标
   都没跑」。
4. **一次判断干扰**：排查时交互 shell 里定义过一个 `grep` 函数，覆盖了命令，让一次输出读起来不对。它只影响交互
   shell，不影响脚本启动的子 bash，但当时花了一点时间才排除。

**怎么发现和修的**：自己搭了一个 stub `go` 加一棵假目标树，stub 记录自己被调用的次数，三种模式都是 0，才知道脚本
根本没走到 `go test`。修法是从 HEAD 取回尾部，用 `git diff -w` 确认非注释改动只剩预期的三处，再用 stub 确认
deadline → rc=1 且只调用一次（不再重试）、crash → rc=1、pass → rc=0，另外实际运行 `go-fuzz.sh 5s "" FuzzLexer`
通过。

## 根因

- **被删的测试有两个角色，名字只反映了一个**。`test-go-fuzz-retry.sh` 的显式用途是测重试逻辑，隐含用途是
  「`go-fuzz.sh` 能端到端跑起来」的唯一证据。按名字判断，它和重试是一起的，一起删理所当然；它的第二个角色没有任何
  地方写着。回头看 [[2026-07-25-issue179-test-go-fuzz-retry-revive-round]]，`test-scripts` 这个 Makefile 目标和
  CI job 当初就是为了让这个脚本不再失效才接进来的，它在 `test-scripts` 里的分量比名字看起来重得多。
- **在同一个 commit 里既改脚本又删掉它的测试**，改动之后能证明脚本还能跑的检查就一个都不剩了。剩下的绿灯不是
  「脚本没坏」的证据，只是「剩下的三个自测没坏」的证据，而它们本来就与 `go-fuzz.sh` 无关。这正是
  [[prove-the-path-under-test]] 的核心断言：绿色不等于在测你以为在测的东西。
- **把「语法通过」当成「行为没变」**。对 shell 脚本来说，截掉尾部几乎总是得到一个语法合法的文件，`bash -n` 对这类
  错误没有区分能力。
- **缩进变化把真实改动淹没了**。去掉一层循环会让循环体整体缩进变化，203 行的 diff 里人眼很难看出多删了一段；
  忽略空白后只有 53 行，多出的那段一眼可见。

## 缺失的文档或信号

- [[prove-the-path-under-test]] §4.6a 讲的是撤掉兜底机制**之前要有多少证据**，没有讲撤的时候**这个机制的测试还顺带
  覆盖了什么**。§4.6 讲 skip 要随 bug 一起撤，同样没有提到撤测试时可能连带撤掉别的覆盖。
- `Makefile` 的 `test-scripts` 帮助文字只按 issue 列每个自测的来历，没有写「哪个脚本由哪个自测端到端覆盖」，所以
  删掉一个自测时看不出会让哪个脚本失去覆盖。
- §4.6a 的 #180 实例停在「本轮明确不删」，没有结局；`llmdoc/index.md` 第 39 行与第 144 行也还是「不删 / 保留」的描述。

## 教训（可复用判据）

### 教训 1：删掉一个机制并连带删掉它的专用测试时，先问那个测试还顺带覆盖了什么

**判据**：删除一个测试之前，列出它**实际执行**了哪些代码（不是它名字说的那部分），对每一项问「删掉之后还有别的
测试执行它吗」。答案是「没有」时，要么保留测试里那一部分，要么在同一次改动里补一个替代检查。自查办法：删完之后
对被改动的每个脚本 grep 一遍剩下的测试里有没有调用它（本轮 `grep -n 'go-fuzz.sh' scripts/test-*.sh` 只在
`test-nightly-fuzz-classify.sh` 的注释里出现，没有任何调用）。

### 教训 2：改写脚本之后，要有一次让它端到端执行、并数一下它调用了什么的检查

**判据**：`bash -n`、lint 与「其余测试全绿」都不能证明一个 shell 脚本还能跑。改完之后至少做一次端到端执行：
用 stub 替换它调用的外部命令并**记录调用次数**，或者实际运行一个最小目标。只看退出码不够，本轮三种模式的
rc 都是 0，是调用次数为 0 暴露了问题。这是 [[2026-07-25-issue179-test-go-fuzz-retry-revive-round]] 教训 1
（shell 判据要配 positive marker）在「检查脚本改动」这一步上的应用：调用次数就是 positive marker。

### 教训 3：用脚本批量改写源文件之后，先用 `git diff -w` 看非空白改动是否只有预期的几处

**判据**：动手前写下「非空白改动应该只有哪几处」，改完用 `git diff -w` 逐处核对，多一处或少一处都要解释。
缩进变化大的改动（去掉或加上一层循环、条件）尤其要这样做。

## 触发场景

- 删除一个功能或兜底机制，并准备连带删除它的专用测试时；
- 用 python / sed / awk 之类的脚本批量改写源文件或 shell 脚本之后；
- shell 脚本改动的全部证据只有 `bash -n`、lint 或「其余自测全绿」时；
- 用「这段时间里 0 次触发」支持删除某个机制时（先找一段同一统计方法数到非 0 的对照期）。
