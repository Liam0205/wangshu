# #296 / #297:arena 大块合并与宿主调用后的 GC 检查(2026-10-05)

> 范围：分支 `fix/296-297-arena-coalesce-host-gc`。对账表和数据在 P1 implementation-progress 的
> 「arena 大块碎片与只靠宿主函数分配的循环」条目，设计在 [06](../../../docs/design/p1-interpreter/06-memory-gc.md)
> §2.4、§3、§7.1,这里只记过程和教训。

## 1. 先修放大另一个的那个

2026-10-05 巡检时先试了 #297:在 `callHost` 末尾加 `MaybeCollect`,递增 `string.rep` 探针的计数峰值从 78 MB 降到
4.6 MB,但固定长度的 `string.rep` 循环 maxrss 从 25 MB 涨到 550 MB,递增长度的循环照样撞上 2 GiB。原因在 #296:
每轮收集末尾 `Compact` 把 slab 缩到 bump,下一个稍大的字符串在 freelist 里找不到够大的块，只能 bump 新切，于是
`grow64` 翻倍扩回。收集越频繁，来回拷贝越多。那次试验撤回，没有提交。

两个修复挡住的是同一类症状(内存不受控)时，先看哪个会被另一个放大。这里 #297 让收集变频繁,#296 的缺陷正好按
收集次数放大，所以顺序只能是先 #296 后 #297。

## 2. 缩容余量挂在 GC 水位上

和用户讨论时比较了两种余量：固定比例，和 jemalloc 那样按收集轮数逐步衰减。决定用固定比例，但比例的基准是 GC 的
下次触发水位，而不是 bump:`target = (live + live × GCPAUSE / 100) × 1.25`,容量超过 `max(target, bump, 64 KiB)`
两倍才缩。理由是堆在下次收集前一定会长到这个水位，缩到 bump 等于确定下一轮要扩回来;两倍与翻倍扩容对应，
稳态下容量不再变。jemalloc 的衰减针对的是不知道未来分配量的通用分配器，这里 pacing 已经给出了下一轮的分配量。

## 3. 改分配器后逐个检查旧用例测的路径

LARGE 块合并加顶部块退回 bump 之后，旧的 freelist 用例大多仍然通过，但有几个是因为释放的块正好在 bump 顶端，
bump 退回后重新从同一地址切出，地址断言碰巧成立，原本要测的分桶、跨桶、余量切分路径都没走到。做法是在被释放的块
后面垫一个 8 字节的小块，让它离开顶端;顶端行为由新用例单独覆盖。判断标准不是「还过不过」,而是「还走不走原来的
分支」;这类改动之后，把每个依赖地址的用例都看一遍。

新用例里的随机模型检查(活块与空闲块互不重叠、相邻空闲块都已合并、没有空闲块结束在 bump、`freeBytes` 与链上
一致)比逐个构造场景更能发现问题;变异检查(去掉清零、去掉向前合并)确认它们会失败。

## 4. 宿主函数分配的测试注意 intern

#297 的嵌入方用例第一版每次返回同一个 64 KB 字符串，修复前也通过：内容相同的字符串经 intern 只有一份，循环根本
没有分配。改成每次返回不同内容后，修复前峰值 128 MB,修复后有界。写「分配很多」的测试时，先确认分配确实发生了:
在去掉修复的树上跑一次，看它失败。

## 5. 顺带改正的说明

`State.ArenaCapKB` 和 `State.Collect` 的 godoc 一直写着「Collect 不缩 backing」,而 `Compact` 早已在 Collect 末尾缩容，
`TestCompact_ShrinkAfterTransientPeak` 测的就是这个;`GCCountKB` 的 godoc 写的是「等于 bump」,实际是 bump 减去空闲块。
改容量策略时，先 `git grep` 所有描述容量行为的说明，一起改。
