# #329：标准库多出两个 5.1 没有的名字

nightly 的 go-fuzz 找到 `t={}table.unpack(t)`：官方 Lua 5.1 报错，望舒照常执行。`table.unpack` 是 5.2 才有的，
设计文档从一开始就写着「不提供」，而实现从 2026-06-11 起多注册了它。顺着查出另一个多出的名字 `__ipairs_iter`，
以及 `pairs` / `ipairs` 经全局表查迭代器造成的两处行为差异。改动清单见
[implementation-progress](../../../docs/design/p1-interpreter/implementation-progress.md) 的 2026-11-25 条目，
机制见 [10 §4.4 / §12.3](../../../docs/design/p1-interpreter/10-stdlib.md)。

## 为什么五个多月没发现

规则是「标准库的名字集合必须与 5.1 一致」。它的执行体只有 `exemptions` 这份手工清单，而清单只能写
「官方有、望舒没有」。「望舒有、官方没有」这个方向没有任何检查。设计文档 §12.3 在 2026-07-29 核对时已经
写明「遍历全部 5.1 函数名的存在性差分用例还没写」，并把它记成缺口，但缺口一直没补。

代码里的注释还把这件事写成了有意为之：`table.unpack alias ... provide both`。注释和设计文档相反，
没有人核对过。

## 这一轮的做法

1. 先按排查指南在当前 master 上精确重放，确认是真缺陷，不是参照实现的问题。
2. 没有只删那一个名字。把两边的名字清单各导出一份比对，一次找出全部两个多余名字。
3. 对第二个名字（`__ipairs_iter`）没有停在「删掉全局」上：它之所以是全局，是因为 `ipairs` 每次去全局表里查它；
   `pairs` 用同样的办法查 `next`。对照 `lbaselib.c` 的 `auxopen`（迭代器是 C 闭包的 upvalue），又找出
   `next = nil` 之后 `pairs` 报错、`pairs({}) == next` 为 `true` 两处差异。
4. 把比对留下来当测试（`TestDiff_StdlibNames`），补上设计文档里记了四个月的那个缺口。

## 可复用的检查方法

写进了 [cross-backend-semantic-fix-sweep](../../guides/cross-backend-semantic-fix-sweep.md)
「两个集合必须相等这类规则，比对要做成常驻测试，而且两个方向都要比」：看到「A 必须等于 B」的规则先问执行体
是什么；执行体是手工清单时，它表达不了的那个方向就是没人看的。

## 独立审查指出的三件事

合入前的独立审查没有发现阻塞问题，但有三处是我自己本该先做到的。

**一、测试写着「热函数」，实际没有升层。** 我假设「循环 3000 次的函数会被升到 P3 / P4」，于是写了一个
在循环里调用 `ipairs` / `pairs` 的用例，注释说它覆盖升层后的路径。实际上直接调用全局函数的函数会被判成
不可升层，这个用例在三种构建下执行的都是解释器。能提前发现它的检查只有一行：读 `PromotionCount()`。
[prove-the-path-under-test](../../guides/prove-the-path-under-test.md) 早就写了「测试通过不证明被测路径被执行」，
我没有照做。改成 `TestTiered_StdlibNames`，把「升层次数大于 0」写成断言。（这仍然不够，见下面「第四轮审查」一段：
升层次数是编译侧的量。）

**二、发现文档与实现不一致，只改了一处。** 核对名字集合时我确认了 `os.exit` 等十个函数没有注册，改了
§14 总表的 os 那一行就停了。同一件事在 README（两个语言版本）、§9.1、§9.3、§9.4、§10.1、§14 的 io 行、
`exemptions` 里还有七八处说法，其中 README 写的「`os.exit` 不真的退出进程」是使用者会照着写代码的。
能提前发现它的检查是在全仓搜索同一个说法（`git grep "os.exit"`），这也是已有的约定。现在由
`TestStdlibAbsentIsInREADME` 检查 README 的「不提供」表与登记表一致。

**三、存量差异没有开 issue。** 我在复盘里写了「这些函数要不要补上，没有在这一轮决定」，但没有留下任何
可以跟踪的东西。按约定，本轮不修的存量差异要开 issue。补开了 #330（os / io 缺少的函数）和 #331
（主块之下的 C 帧，栈回溯按独立解释器、C 调用深度按内嵌用法）。

审查还指出 `ipairs` 的迭代器不接受数字字符串。这是存量差异，但它就在这次改动的函数里，而且属于同一类
原因：迭代器没有公开的名字，以前按函数名逐个核对 `luaL_checkint` 的行为时轮不到它。这一轮直接修了。

**第二轮审查又找到六处同一说法的副本。** 第一轮之后我按「`os.exit`」搜了一遍，改了 README 和 10 号文档，
仍然漏掉了 11、12 号文档、`embedding-contract`、`doc-gaps` 和决策归档，新写的一句话还把两个宿主开关写成了一个。
漏掉的原因是搜索词太窄：这组说法在各处的写法不同（「不真退」「默认面对齐 gopher-lua」「三层禁用机制」
「`Options.Libs`」）。改一个事实的时候，要按这个事实涉及的每个名词各搜一遍，而不是只搜触发问题的那一个词；
新写的陈述句（「宿主能调的只有……」）要对着代码核对，这里应该对着 `wangshu.go` 的 `Options`。

**第三轮审查指出我给自己写的检查也有盲区。** `TestStdlibAbsentIsInREADME` 是我为了防住「README 与登记表不一致」
加的，我只用三四种删除试过它会失败，就在进度记录里写了「README 删掉一行或一个名字，测试会失败」。reviewer 对
35 个名字逐个删除，发现其中 4 个不会失败：匹配是在整行里找词，英文原因栏里的 input、output 正好是函数名；
debug 那一行的缩写正好是全局函数的名字。教训有两条。检查「集合 A 的每个元素都在 B 里」的测试，要对 A 的**每个**
元素做一次变异，而不是抽几个；一句「删掉任何一个都会失败」只有逐个试过才能写。在一段自然语言里按词匹配
标识符是不可靠的，要先把结构切出来（这里是表格的「具体项」一栏）再匹配。

同一轮还指出 `io.lines` 的修复没有升层路径上的测试。第一轮我刚因为同一个问题被指出过（标着「热函数」的用例
没有升层），第二轮顺手修 `io.lines` 时又只写了解释器上的测试。「每个行为修复都要有一条在升层路径上执行的用例」
应该在提交之前逐个修复点核对，而不是只对最初的那个问题核对。

**第四轮审查指出分层测试仍然没有在升层代码里执行。** 第一轮之后我把测试改成断言 `PromotionCount() > 0`，以为这就
证明了「在测升层路径」。它只证明内核被编译了。出错路径我写成 `pcall(kernel, 坏参数)`，而被宿主函数调用的 Lua 函数
固定由解释器执行，所以四段脚本里有两段升了层、一次也没在升层代码里跑过；reviewer 只改升层路径的报错分支，测试照常
通过。[prove-the-path-under-test](../../guides/prove-the-path-under-test.md) 开头就写着「这类计数器还要问它是编译侧
还是执行侧，一个编译了但从未调用的函数是否也让它增长」，我用了一个编译侧的计数器。同一个问题被指出了两次：第一次是
「没升层」，第二次是「升了层没执行」。能提前发现它的检查是那条指南里已有的做法：只改被测路径做一次变异，看测试是否
失败。我对标准库做了变异，没有对升层路径做。

这一轮加了执行侧的探针 `State.GibbousEntries()`，并把规则写进指南 §2.2c。用它扫现有语料，`p4Corpus` 里还有 12 个
出错用例是同样的写法（#333）。

同一轮还指出我上一轮为补测试加的语料，把一处已知差异（`io.lines(文件名)`）放到了离 fuzz 只有一步变异的地方。往差分
语料库里加一条语料之前，要先问：把它的每个参数换成别的类型，两侧还一致吗？不一致的那些要么先在 prelude 里处理，
要么不加这条语料。

**第五轮审查没有找到行为和测试上的问题，剩下的三条都在文字上。** 其中一条是我在上一轮改 `f:setvbuf` 的理由时，
照着 `tablelib.go` 里一段旧注释写了「读 stdin 经过 State 自己的 `bufio.Reader`」，而那段注释本身与代码相反
（reader 是进程内共享的）。写进文档的事实要对着代码核对，注释不算证据。另一条是我把「以前是怎么错的」写进了十几处
代码注释和设计文档正文。这些经过只应该记在这份复盘和 `implementation-progress.md` 里，正式文档和注释只写现在的
行为和约束；每一轮修完都在正文里留一句「此前……」，读的人要先分清哪句是现状。

**第六轮的四条小问题里，有两条出在我上一轮顺手改的地方。** 第五轮把 `debug.getinfo` 字段说明不完整列为存量问题，
我只实测了默认选项下返回哪些键，就改了七处文档，没有测「按栈层级查询」和「带选项」这两种形式，结果新写的句子仍然
不准；同一张表里紧挨着的两行（`debug.setmetatable` 标着「必做」）我也没有看。动一处修改前就不准的文档时，范围是
这句话所在的整张表或整段，要把它列出的每一种情况都实测一遍；做不到就不要动它，开 issue 登记。清理「以前怎么错」
的句子时我靠关键词检索，漏了五处换了说法的；后来把分支新增的注释和文档逐行读了一遍，这才是该用的办法。

**`debug.getinfo` 的字段说明连续三轮（第六、七、十一轮）被指出不准。** 每次我都是在七处各补一句。同一个事实写在七处，
每处都是凭当时测到的那几种形式写的，所以每一轮总有一种形式没测到（先是按栈层级查询，再是选项，最后是 C 帧）。第十一轮
才改成正确的做法：先把查询形式列全（函数参数分 Lua 和 C，栈层级分 Lua 帧、C 帧、尾调用帧，再加越界、负数、协程参数），
逐个与官方对比，做成一张表放在一个地方，其余位置只留不随形式变化的话并指向它。一个事实需要在多处出现时，只在一处
写全；多处各写一遍，等于留下多份都不完整的副本。

**第十三轮才发现分层测试在 arm64 的 P4 上会失败。** 前十二轮审查和我每一轮的自查都只在 amd64 上执行；reviewer 报告的
「验证的限制」里每一轮都写着「arm64 没有执行」，我把它当成例行说明，没有当成待办。#329 的内核里有一条读不存在字段的
`GETTABLE`，P4 的原生翻译不接受它，amd64 靠 head-op replay 仍然升层，arm64 没有这条路径，「强制升层进入过升层代码」的
断言在那里不成立。仓库里早有同一种不对称的先例（`test/fuzz` 的 `topPromotes`），项目记忆里也有一条「arm64 与 amd64
不对称」，写测试时我没有去查。这台机器其实能执行 arm64 的测试：下载 `qemu-user` 的包解压到临时目录（不需要安装），
用里面的 `qemu-aarch64` 运行交叉编译出来的测试程序即可。断言依赖「某个后端会不会编译这个函数」时，要在每种架构上
执行一遍；审查报告里反复出现的同一条验证限制，要么消除它，要么明确写出它挡住了哪条结论。

**第十三轮的一条文字问题我修了四处，漏了两处，被下一轮的复核指出。** 我查同一说法时用的是 `其他非字符串`、`非字符串报`、
`non-string` 这几个字面写法，目录只给了文档、`internal/stdlib` 和 `test`。漏掉的两处一处在 `internal/oracle`，一处的写法是
「布尔值、表等非字符串时」，都不在检索范围里。查同类说法要按「这句话在说哪个事实」来找（这里是「`io.lines` 的参数按类型
怎么分」），把分支里提到这个函数、又提到类型的新增行都读一遍，不限定目录；按原句的字面写法检索只能找到照抄的副本。
同一轮我给 lint 的条数开 issue 时直接用了工具打印的总数，没有注意它默认每个 linter 只报 50 条，其中一类正好是 50。
工具的计数出现上限值那样的整数时，要先查它有没有截断。

**第十七轮指出 `io.lines` 带文件名的分支没有任何测试，这是我自己改写的函数。** 前十六轮里我和各位 reviewer 加起来做了
几十种变异，每一种都被测试发现，我据此认为「测试会在问题重现时失败」成立。这些变异都是从「我修了什么」出发挑的：把修掉
的行为改回去。`ioFnLines` 有五个分支，我的修复动了其中三个，另外两个（数字也算文件名、带文件名时报错）我只是照着官方
源码写了出来，没有哪个测试经过。差分 fuzz 的语料里有带文件名的调用，但 prelude 在它到达望舒的 `io.lines` 之前就把它换成了
harness 错误，那条语料测的是 prelude。之后我把分支对产品代码的全部改动列出来逐个分支做变异，又找到两处同样的缺口。
变异检查要按被改函数的分支枚举，一个分支一种，而不是按「这次修了哪几个行为」枚举；一条语料或用例覆盖的是哪一层，
要看它实际走到了哪里，包装层拦下的输入不算被包装的函数的覆盖。

## 顺带核对出的文档错误

`10-stdlib.md` 把 `os.exit` / `os.remove` / `os.rename` / `os.tmpname` / `os.setlocale` 和
`io.close` / `io.flush` / `io.input` / `io.output` / `io.type` 写成「做简化版」，README 写「os 全部提供」，
实际都没有注册。设计文档里的 `Libs` / `LibsSafe` / `Exclude` 三层开关也没有实现。这次把 README 和设计文档
各处都按现状改了（设计文档新增 §9.5），原始设计的段落保留并标明不是现状。这些函数和开关要不要做，
记在 [#330](https://github.com/Liam0205/wangshu/issues/330)。

方向相反的错误也有：设计文档说 `table.getn` / `setn` 不提供，实际一直提供；总表没有列 `table.foreach` /
`foreachi`、`math.mod`、`string.gfind`。这些也改了。设计文档的逐函数表格没有任何常驻检查，这一轮三次审查
每次都在里面找到不一致，记在 [#332](https://github.com/Liam0205/wangshu/issues/332)。
