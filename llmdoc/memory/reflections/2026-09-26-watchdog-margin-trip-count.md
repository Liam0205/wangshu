# watchdog-margin 测试改为圈数断言（2026-09-26，PR #268）

承 [[2026-08-04-issue224-225-watchdog-margin]] 教训 4。那一轮把上界改成推导出的 250 毫秒，并实测它能
抓住 `1<<19` 与 `1<<20`；但那个结论只在**不带 `-race` 的本地构建**里成立，而 PR CI 跑的是 `-race`。

## 经过

1. **`-race` 下的耗时量的不是预算**（`fddb940`）。`-race` 让这些写法慢约 10 倍，耗时主要反映 race
   detector 和 runner 负载。macos-latest 上 2.538 秒对 2.5 秒上限失败，代码没有改动。先把 `-race` 下改成
   只记日志，另在 nightly p4 腿加一个不带 `-race` 的步骤，用 2.5 秒（10 秒 / `FuzzAutoPromote` 的 4 次 Run）。
2. **2.5 秒本身没有余量**（`61daaa8`）。PR 审查实测把预算放大到 `1<<19` 时它照样通过，而且此时 PR CI
   已经完全不断言时间。于是换成圈数：每个写法的循环把计数器写进全局 `ITER`，预算触发后读它。这个数只由
   预算和计费决定，默认、`wangshu_profile`、`-race` 三种构建下完全一样，预算翻倍它也翻倍（gsub：`1<<16`
   507、`1<<17` 1015、`1<<20` 8127）。只断上侧、留 25% 余量；`1<<17`、`1<<19`、`1<<20` 与「每字节计费
   减半」在默认和 `-race` 构建下都失败。18 个写法里 17 个带循环，`single insert just under the shift cap`
   只有一次调用，不参与计数。
3. **耗时退到它独有的那一类**：计费不变而操作变慢。本地 250 毫秒；nightly 800 毫秒，约 2.5 秒的三分之一，
   按 GitHub Linux runner 在 `1<<20` 的实测线性投射到 `1<<16` 约 0.2 秒，所以约 4 倍变慢才会报。
4. **triage 分类**（`5769ffe`）。步骤跑在 `always()` 下，checkout / setup-go / 拉依赖失败也会让 outcome
   变成 failure；只看 outcome 会把 infra 故障开成 `watchdog margin regression`。现在还要求日志里有测试的
   `=== RUN` 行（超时和被取消的情况也带这一行），自测覆盖空日志、依赖下载失败、启动前取消。
5. 设计文档 `engineering.md` §3.2、`12-testing-difftest.md`、P4 `08-testing-strategy.md` 同步改成圈数描述
   （`db7d415`、`2e09072`、`34683bd`、`4e8bf27`）；有意调 `fuzzbudget.Steps` 或计费比率时要重新记录这 17 个圈数。

## 教训

### 教训 1（预算的回归要断言预算直接决定的确定性量）

**Why**：预算限制的是计费单位，墙钟只是它在某台机器上的投影，会被构建（`-race`）、runner 类别和负载放大
一个数量级（参见 [[2026-08-09-runner-wall-clock-assertion-audit]]）。拿墙钟当主断言，要么上界宽到放过被防的
回归，要么窄到在别的机器上误报；这次两种都遇到了。

**How to apply**：判据 = 给资源预算写回归测试时，先找「只由预算和计费决定、与机器无关」的量（这里是预算触发
时的循环次数），在所有构建里断言它；墙钟只防这个量看不见的「同样计费、更慢」，并且只在它有意义的构建和
runner 上断言。自查：同一个测试在默认 / `-race` / 另一类 runner 上读到的是不是同一个数；不是，就说明它量到了
机器。

### 教训 2（「已用变异实测确认」要带上是在哪个构建里测的）

**Why**：2026-08-04 那轮的变异实测是真的，但只在本地默认构建里做；实际执行这条断言的 PR CI 是 `-race`，
后来又把 `-race` 下的断言关掉，于是「能抓住 `1<<19` 与 `1<<20`」在 CI 真正走的路径上悄悄失效，文档没跟着改。

**How to apply**：记录一次变异确认时写明构建和执行位置；之后改动「哪个构建断言什么」时，回头检查依赖那次
确认的说法（→ [[prove-the-path-under-test]] §2.2「能编译不等于进了那条路径」）。

### 教训 3（always() 步骤的失败分类要先确认被测对象启动过）

**How to apply**：`if: always()` 的步骤失败时，outcome 不区分「被测对象失败」和「前置失败」；按 bug 分类前
先在日志里找被测对象已经启动的标记（`=== RUN`），并给「没启动就失败」写自测用例。
