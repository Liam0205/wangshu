# 两个问题我都先诊断错了(2026-08-19,commit `9b61079`)

> 范围:分支 `fix/nightly-step-timeouts-and-budget`,1 个 commit `9b61079`,只改了
> `.github/workflows/nightly-diff-fuzz.yml`。产品代码零改动。

## 任务

nightly fuzz job 一周内被 job 超时掐掉三次(2026-08-12 p4、2026-08-15 p4、2026-08-18 p1),其中
两次真丢了覆盖。两个独立问题,而**两个我都先诊断错了,是量出来才纠正的**。

## 问题一:步骤无界——我上一轮的修法只框住了症状,不是那一整步

`#236–#241`(PR #242)那轮我给取包脚本 `fetch-lua-tarball.sh` 里的 curl 加了
`--max-time 120 --retry 4`。但**装 oracle 那一步里有四条命令**:`apt-get`、
`fetch-lua-tarball.sh`、`make -C lua-5.1.5`、`check-oracle.sh`——**我只框住了当时报错的那一条**,
另外三条留在原地,无界。

2026-08-18 那轮 p1 就在这一步卡了**5 小时 50 分**,被 job 超时掐掉,几乎丢了整轮覆盖:
rolling-seed 与 auto-mode 被 skip、两个 go-fuzz 步骤根本没启动。

**普查之后发现无界的步骤是三个不是一个**:装 oracle、upload logs、triage。三个步骤,一个都没有
step 级超时。

### 为什么会犯这个错

给一条报错的命令加超时,读起来像「这个问题解决了」——那条命令确实不会再无限挂。但它的邻居没有变。
「作用域=命令」这个错误没有任何自动信号:测试(如果有)会测那条被改过的命令,不会测它的邻居;下一次
从邻居那里挂,症状是全新的(不同的命令、不同的日志),看起来像一个新问题,而根因是同一个——诊断
时**范围**没有选对。

## 问题二:预算——我连推荐了五轮的方案是无效的,而我从没量过真正的成本中心

我连续五轮建议「把 auto-mode 从 150m 压到 90m」。**实测之后发现这个建议省不下任何时间**:
auto-mode 实际只跑 **2 分钟**,它那个 150m 是防挂死的上限、从来没接近过。

真正的成本中心是 native go-fuzz 那一步:**312 分钟的 job 里它占 270 分钟(87%)**,而我一直没量
过它。

### 为什么是 270 分钟

`go-fuzz.sh` 用**源码扫描**发现目标、每个目标跑满 fuzztime,而**无 tag 的源码可见目标有 6 个**
不是 workflow input description 里写着的「4 targets」:root 包的 `FuzzCompileRun` /
`FuzzAutoPromote` / `FuzzP4ForceAllPromote`,外加 `internal/frontend/lex` /
`internal/frontend/parse` / `internal/stdlib` 各一个(`FuzzOracleDiff` 被
`wangshu_oracle_cgo` gate、在自己的步骤里跑,不算在这 6 个里)。**6 × 45m = 270 分钟,与实测完全
吻合**——这个过时的「4」正是这一步成本被长期低估的原因。

### 修法

`gofuzztime` 从 45m 降到 35m(6 × 35m = 210 分钟),job 约 250 分钟、余量从约 38 分钟升到约
98 分钟。**这是真的减少了约 22% 的每轮探索量**,是明确的取舍;选它而不是砍差分步骤,因为差分步骤
实际很便宜(rolling-seed 36 分钟、auto-mode 2 分钟)而这一步占 87%。同时把 description 里的
「4 targets」改成「6 untagged targets」。

### 为什么会犯这个错

我在推荐「压 auto-mode」时手里没有任何一步的实测耗时,推理链是「auto-mode 上限最大,砍它收益最大」
——这是把**上限**当成了**实际成本**,而这两者只有在「机制总是逼近上限」时才相等,auto-mode 完全
不是这种情况。真正决定成本的那一项(native go-fuzz)反而是我从没起疑过的,因为它的表面数字看起来
「合理」(45m per target,听起来不大)——直到「per target」乘上真实的 target 数才现出原形。

## 另外两条我自己纠正的错误

### ①「抬到 420」不可能——我从没查过平台限制

我连提四轮的「把 timeout-minutes 抬到 420」是不可能的:GitHub 托管 runner 单 job 硬上限
**360 分钟**,设 420 也会在 360 被杀。我推荐了四轮却从没查过平台限制,推荐的数字本身就是错的、
不是「效果不够好」。

### ②「step 上限之和必须低于 360」这个框架本身是错的

我据此算出 p3 最坏 548 分钟、得出「只能大幅压缩」的结论。**正确的框架是**:job 超时才是预算,
step 上限的作用是让一条卡死的命令不能悄悄吃掉这个预算,**两者是不同的事**。按「求和」去配会逼出
远超实测成本的削减——本轮最终配的 step 上限(12+300+120+15+10=457,加两个 `-timeout` 内含的
150m×2)加起来远超 job 的 350m,而这完全没问题,因为它们不是同时全部命中上限;真正的约束是
job 的实测总耗时(约 250-312 分钟)低于 job timeout(350 分钟)。

## 要写进去的教训

1. **一个「加超时」的修复,作用域应当是步骤而不是那条报错的命令。** 我给报错的 curl 加了界,
   同一步里三条邻居命令留在无界状态,下一次就从邻居那里挂了 5 小时 50 分。判据:给某条命令加超时前,
   先列出**同一执行单元里所有命令**,并优先选一个对「以后新增的命令」也生效的机制(step 级
   timeout 而不是逐条包 timeout)。这是「定位到一个分支后要对遍它所有出口」在 CI 配置上的形式。
2. **推荐一个数值之前,先查这个数值有没有平台上限。** 我连提四轮「抬到 420」,而 GitHub 单 job
   硬上限是 360。判据:任何「把某个配额调大」的建议,都要先确认**调大的空间存在**;写下数字的
   同时写下它的上界来源。
3. **优化建议必须先量成本分布,否则会推荐一个省不下时间的改动。** 我建议压缩 auto-mode 五轮,
   而它只占 2 分钟;真正占 87% 的那一步我从没量过。判据:提「压缩 X」之前,把同一预算里**每一项的
   实测耗时**列一遍,再看 X 占几成;占比小于一成的项,压缩它只会降低上限、不改变实际时长。
4. **一个陈旧的计数会让成本被长期低估,而它不会自己报错。** description 里的「4 targets」写着,
   实际是 6 个,于是这一步的预算被低估了三分之一,而 6 × 45 = 270 与实测吻合说明这个数就是关键
   参数。判据:凡是「per X」的配置项,都要核一遍 X 的实际数量;这类数字在数量变化时不会有任何
   自动信号。
5. **「让各项之和不超过总额」与「让任何一项都不能吃掉总额」是两个不同的目标,用错会逼出过度削减。**
   我按前者算,得出 p3 最坏 548 分钟、必须大幅砍;按后者只需给每步一个够宽的上限。判据:给一批
   步骤加超时时,先问「我要防的是总量超支,还是单点卡死」;是后者时,上限按**该步实测的 1.5~2 倍**
   取,不要试图让它们求和。

## 触发场景

- 给一条报错的命令加超时前 → 先列出同一执行单元里所有命令,优先选 step 级机制(教训 1)。
- 推荐调大任何配额 / 上限之前 → 先查平台硬上限(教训 2)。
- 提「压缩 X 来省时间」之前 → 先量整个预算里每一项的实测耗时,看 X 占几成(教训 3)。
- 读到 / 写下「per target」「per item」这类配置描述时 → 核一遍那个数量的实际值(教训 4)。
- 给一批步骤 / 一批资源加上限时 → 先问防的是总量超支还是单点卡死,答案决定用求和还是用独立上限
  (教训 5)。

## 审计逐轮补正

四轮独立审计加一轮 PR review,每一轮都找出一个我定错的值,而**每次我都只修上一个反例指出的那一侧**。
保留过程,因为过程比结论有用。

- **实测补正**:各层跑到的目标数不同 —— p1 4 个、p3 5 个、p4 6 个 target-run,
  所以 45m 下三条腿约 180 / 225 / 270 分钟(p4 恰好 6 × 45),35m 之后约 140 / 175 / 210 分钟。
- **第二轮**:#75804 的重试是**按目标**而不是按腿的,两个目标各重试一次就是 210+35+35 = 280,
  而我当时正好取 280 —— 在一次**健康**运行上把余量吃光。另外三步仍只有内层 `go test -timeout`,
  而我在 commit 里已经声称「bound every step」。
- **第三轮**:取 320 时这个上限**永远不会生效** —— 前置约 40 分钟,它在约 360 触发、已在 350 之后。
  约束是**两侧**的:要盖过合法最坏情形,也要在 job 上限之前触发。
- **PR review**:两个 `uses:` 步骤仍无界;而且更要紧的是,后面的步骤都是 `if: always()`,
  所以**光把这一步框住不够** —— 要满足的是「前置 + 本步上限 + 后面每一步的上限 < job 上限」。
  p1 的尾巴含 oracle-diff(80+15+10 = 105),而 p3/p4 只有 25,所以这个上限必须**按层取值**:
  p1 195、p3/p4 280。实测三层分别是 340 / 347 / 347 分钟,都在 350 以内。
- **PR review 第三轮**:`gofuzztime` 是自由输入而 step 上限是定值,两者可以不一致 —— 手动派发 45m 时 p4 六个目标基础就 270 分钟、再有一次重试就超过 280 上限被截断,而**被截断的 fuzz 看起来与「跑完了但没发现」完全一样**。现在派发前有一步显式校验:「一遍 + 一次重试」超过上限就**直接失败并给出建议值**(重试是实测的常规事件,9/450),只有「第二次重试放不下」才是警告 —— p1 的 195 就属于这一类,是为了给尾巴留出 triage 的余量而明确接受的。判据:一个可配置项与一个定值上限并存时,要有一步把两者对上,否则不一致会以「静默少测」的形式出现。
- **一处自查失误**:我写脚本核验可达性时用子串匹配查每步耗时,
  而 `auto-mode rolling-seed diff` 同时含有 `auto-mode` 与 `rolling-seed`、先命中后者,
  于是给它记了 36 分钟而不是 2 分钟,前置被算成 74、脚本报「300 也不可达」。
  判据:用名字做键查表时,先确认没有一个名字能匹配多个键 —— 这类错误不报错,只给一个看似严谨的错数字。
